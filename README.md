# Of Wild & Walls — Phase 2

Photography portfolio for Of Wild & Walls, rebuilt under SOW-002. One Next.js app holds the public site, the
Payload CMS admin (`/admin`) and the API (`/api`), backed by PostgreSQL.

- **Stack:** Next.js 16, Payload CMS 3, PostgreSQL 16, S3-compatible storage (AWS S3 / Backblaze B2 / GCS)
- **Hosting:** AWS EC2 (app + background job worker)
- **Design docs:** database design and build plan live in the claude.ai project "ofwild"

## Local setup

Requirements: Node 22.23+ and pnpm 10.

```bash
pnpm install
cp .env.example .env            # then set PAYLOAD_SECRET
docker compose up -d            # local Postgres on :5432 (or use your own)
pnpm migrate                    # create the tables
pnpm dev                        # http://localhost:3000, admin at /admin
```

The first visit to `/admin` asks you to create the admin account. After that, new accounts can only be
created by a signed-in admin (the site has a single admin login, no roles).

Without `S3_BUCKET`, uploads are stored on local disk in `./media` — fine for development.

## Scripts

| Command | What it does |
| --- | --- |
| `pnpm dev` | Dev server |
| `pnpm build` / `pnpm start` | Production build / server |
| `pnpm migrate` | Apply pending migrations |
| `pnpm migrate:create <name>` | Generate a migration after changing a collection |
| `pnpm generate:types` | Regenerate `src/payload-types.ts` |
| `pnpm generate:importmap` | Regenerate the admin import map after adding admin components |
| `pnpm jobs:run` | Run the background job worker (bulk upload processing) |
| `pnpm lint` / `pnpm typecheck` | Checks |

Schema changes always go through migrations (`push` is off): change a collection, run
`pnpm migrate:create <name>`, review the generated SQL, commit it, then `pnpm migrate`.

## Project structure

```
src/
├─ app/
│  ├─ (frontend)/        public site (Flow canvas, Grid, photo view)
│  └─ (payload)/         admin + REST/GraphQL API (generated by Payload, don't edit)
├─ collections/          one file per table (see below)
├─ fields/               shared fields: slug, status, sort order
├─ access/               access rules (public vs admin)
├─ lib/                  EXIF reading, gear matching, text helpers
├─ migrations/           database migrations
└─ payload.config.ts     wires collections, storage and plugins together
```

## Data model

| Collection | Table | Purpose |
| --- | --- | --- |
| `photos` | photos | Uploaded photos + metadata; EXIF fills camera, lens, settings and date on upload |
| `categories` | categories | Nested (Wildlife > Big Cats > Tigers); `path` holds the slug chain for filters |
| `photo-collections` | photo_collections | The client's "Collections" (trips, series) |
| `locations` | locations | Where a photo was taken |
| `cameras`, `lenses` | cameras, lenses | Gear; EXIF spelling variants matched through `exifAliases` |
| `tags` | tags | Free-form tags, searchable but not a filter |
| `media` | media | RAW versions (Edited/RAW toggle) and ambient audio |
| `bulk-upload-batches`, `bulk-upload-rows` | bulk_upload_* | Bulk Upload page: one row per Google Drive link |
| `users` | users | The single admin login |

Rules worth knowing:

- Categories and collections can't be deleted, only **hidden** or **archived**, so photos never lose their links.
- Public visitors only see photos with status `published` and categories/collections with status `active`.
- Camera and lens names from EXIF are matched case- and space-insensitively; unknown ones are created and
  marked **Needs review** so the admin can give them a clean name.
- Search uses trigram indexes on photo title, species and tag name (`migrations/*_search_trigram_indexes.ts`).
